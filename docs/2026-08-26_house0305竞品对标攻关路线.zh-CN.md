# 2026-08-26 house0305 竞品对标攻关路线

主线自本日起转向 house0305 数据集（2026-03-05_10-58-54 RTK house 记录）。它带有竞品
软件的高质量输出 USAgs.ply——**第一次有了"这套数据条件下实际可达"的目标，而不是只有
照片的 1.000**。

## 一、竞品配方（从文件读出，非猜测）

| 属性 | USAgs.ply | 我们的 R0（此前最佳） |
|---|---|---|
| 高斯数 | 22,452,075 | 390,901 |
| LiDAR 点数 | colorized.las 18,757,869 | 同源（ukgs 稀疏采样 390k） |
| 高斯/点 比 | **1.20** | 1.00 |
| 最长轴 p50 | **4.4 mm** | 64 mm |
| 最短轴 p50 | 0.4 mm | — |
| 长宽比 p50 / p95 | 10.2 / 59.6 | ~6 / 25 |
| 球谐 | **0 阶（无视角相关色）** | 3 阶 |
| 不透明度 p50 | 0.197 | — |
| 坐标系 | 与 colorized.las 同帧（范围吻合、中心近原点） | — |

**配方 = 稠密 LiDAR 逐点转毫米级微高斯 + 位置信任传感器 + 只优化颜色/不透明度 +
几乎不做致密化搜索。** DATASETS.md 早有记录：mipmap 在另一数据上输出 4855 万高斯
（gs.ply 2.53GB），同一风格。

这逐条印证了 R 系列阶梯的结论（位置质量是约束、致密化净负、R0 输在初始化密度差 48
倍），也印证了 WP-6 的固定容量方向。SH0 同时是显存取舍：22M×SH3 训练态 ≈ 18GB 装不
下，SH0 只要 ~4-5GB。

### Phase B：量化目标（接入完成后立刻）

写 `tools/import_gaussian_ply.py` 把 USAgs.ply 装进我们的 checkpoint 参数面
（SH0 → sh0 有值、shN 空），然后：

1. 渲一个验证视角确认坐标系（画面对上 = 同帧成立）；
2. `sharpness_metrics` 在验证视角测竞品的 **energy / agreement / holes**——
   这三个数字就是本攻关的量化目标；
3. 若竞品数字意外地低但肉眼确实好 → 先校准判据（第一次有已知好的参照物可校准）。

### Phase C：稠密初始化阶梯（核心实验）

**不致密化**（R0 语义：refine 窗口推到 max_steps 之外），只动初始化密度与相应参数：

| 臂 | 初始点数 | init_scale_m | SH | 训练态显存估算 |
|---|---|---|---|---|
| H1 | 2M | 0.020 | 3 | ~1.9 GB ✓ |
| H2 | 6M | 0.012 | 1 | ~2.2 GB ✓ |
| H3 | 18M | 0.008 | 0 | ~4.2 GB ✓（竞品对位臂） |

init_scale_m 按采样点距缩放，使总覆盖面积 N·r² 跨阶梯大致守恒（R0 是 390k×(5cm)²
≈ 977 m²；H1≈800、H2≈864、H3≈1200 m²），避免"密了但全是洞"或"密了但糊成一片"。

其余参数**全部锁定 R0 值**（单变量纪律）：`max_steps 16000`、`factor 2`、
`rgb 0.8 L1 + 0.2 SSIM`、`lidar_range_weight 0.02`（消融证明对画面免费、买几何）、
法线对齐开（消融证明 +0.013~0.017）、seed 42。

判读（预写死）：
- H3 一致性接近竞品实测值 → 初始化密度就是全部答案，进入产品化（收敛速度、显存、
  分块）；
- H 阶梯单调上升但到不了竞品值 → 密度必要不充分，差值部分逐维归因（能量→颜色优化；
  空洞→不透明度/尺度初值；一致性→位姿质量，跑 reprojection audit）；
- H 阶梯不升 → 初始化密度假说错，回到判据校准。

### Phase D：收口

- 赢家臂跑 30k 正式 + 导出 ply，与 USAgs 同视角出图对比；
- 结论进 runs.csv + 阶段文档；把可产品化参数写成 preset。

## 三、结果（2026-08-26 阶梯跑完）

### 关键修正：之前的比较口径是错的

用户告知竞品的天空是**单独的 sky.ply**（无限远背景球），而该文件未提供。实测本场景
**78–85% 的像素没有 LiDAR 回波**（激光打不到天空，因此"无深度支撑"是天空的直接判据）。
所以此前所有整帧数字：

1. 大部分在比天空，而竞品缺了那一层——对它不公平；
2. 平滑天空稀释了双方的能量，掩盖了真正有分歧的几何部分。

`sharpness_metrics` 新增 `--exclude-sky`（限制到有 LiDAR 支撑的像素）与
`--crop-metrics`（区域内单独计算，此前两套截图会打印完全相同的整帧数字）。
**phase18 自带的所有测量与判读作废**，统一由 `remeasure_ladder.py` 重测。

### 阶梯结果（全部排除天空、房子区域、latest.pt @16k、births off）

| 臂 | 初始点数 | 尺度 | SH | 能量 | 一致性 | 空洞率 |
|---|---|---|---|---|---|---|
| H1 | 1.86M | 20mm | 3 | 0.652 | 0.334 | 0.3% |
| H2 | 5.47M | 12mm | 1 | 0.724 | 0.342 | 0.3% |
| **H3** | **15.9M** | **8mm** | **0** | **0.771** | 0.345 | 0.5% |
| 竞品 | 22.45M | 4.4mm | 0 | **0.813** | 0.145 | 0.5% |

几何整体（排除天空，不限区域）：0.564 → 0.634 → 0.693，竞品 0.744。

**密度是主因，但单靠密度关不上差距。**

- 增益在饱和：第一次 2.94 倍买到 +0.072，第二次 2.91 倍只买到 +0.047；
- H2 记录中**预先登记**的外推是 ~0.79，实测 0.771，说明关系向下弯；
- 用三臂对 log(点数) 拟合并外推到竞品的 2245 万点，得 **0.794**，而竞品实测
  **0.813**——**差 0.019 是再多点也解释不了的**。

结论：原始差距约三分之二来自初始化密度，其余来自别处。候选：**高斯尺寸**
（竞品 4.4mm vs 我们这一档 8mm）、优化器调度、逐图颜色处理。**下一步不是继续加点。**

覆盖率已追平（双方 0.5%）。一致性我们仍高一倍（0.345 vs 0.145），但该项跨流水线不可比
——我们训练在这套位姿上，竞品刚性对齐后仍有几厘米局部形变，逐像素梯度相关对此极敏感。

### 必须记录的混杂

SH 阶数沿阶梯从 3 降到 1 再到 0（为装进显存），因此**并非严格单变量**：密度上升的同时
视角相关色能力下降，而能量仍上升——这如果有偏，是**低估**了密度的作用。

### 两个基础设施故障

- **H3 首次死在第 0 步**：`torch.quantile` 有 2²⁴ 元素上限，1590 万高斯有 4770 万个尺度值，
  **只负责描述训练的遥测代码把训练本身打死了**。已改为 min/max 取全量、中间分位数按确定性
  步长降采样，并补三个回归测试（此类故障随模型规模出现，最贵的一臂才会碰到）。
- 磁盘两次触顶：周期性评估渲染图占 54GB 而全部指标 JSON 只有 0.03GB；已确立"删图保 JSON"
  的清理惯例。

## 四、纪律（本轮教训的固化）

- A/B 一律 `latest.pt` 固定步数；`best_golden` 只回答"发布哪个"（它曾把 R2 排名整个
  倒置、让 R5 的 manifest 计数骗人）；
- 每臂跑前查磁盘（现 51 GB，H3 checkpoint ≈ 1 GB/个）；
- 竞品 ply 与原始数据**只读**；
- 每节点 runs.csv + commit + push machine-b/uk-quality + 同步 origin/master；
- **跨产品比较必须排除天空**（`--exclude-sky`），并说明对方是否有我们没拿到的图层；
- 外推在被验证的臂跑完**之前**写进记录，否则事后都像"早有预料"。

## 五、下一步（按剩余差距的归因排序）

剩余 0.042（房子区域 0.771 → 0.813），其中约 0.019 密度解释不了。

1. **高斯尺寸**：竞品 4.4mm，H3 是 8mm。可在 H3 的点集上直接扫 `init_scale_m`
   （8mm / 6mm / 4.4mm），单变量、不动密度。这是最直接对位的一项。
2. **色彩与曝光**：两边色调差异肉眼明显（竞品偏暖，我们偏灰蓝）。查 `exposure_compensation`
   与 PPISP 的实际作用，这对观感的影响可能比锐度更直接。
3. **训练长度**：H 阶梯统一 16k。竞品未知，若把赢家臂拉到 30k 可验证是否还有余量。
4. **拿到 sky.ply 后**：合并重测竞品完整水平，届时可去掉 `--exclude-sky` 做全画面对比。

暂不做：继续加初始化密度（已饱和）、重开致密化（R 阶梯已证明净负）。

## 六、P0 发现（2026-08-26 深夜）：位姿漂移 + 验证集塌缩，此前全部指标只看了一个角

用户检查 H3 导出 ply 后报告：**只有车棚一侧像训练过，另一侧完全是零碎错误颜色**。
复查证实，且根因有两层，互相掩护：

### 6.1 验证集塌缩（度量盲区）

`house0305_evaluation` 配置写的是 `temporal_block × 10`，但实测 **90 张验证帧全部落在
采集开头 22 秒**（第 0 个时间十分位），即车棚角。整场战役的 energy/agreement/对比图
（视角 42/60/78）都在这个角测量，**场景其余 90% 从未被任何验证渲染过**。切分器
`rig_frame_split_v1` 的时间块实现有 bug，待修＋补回归测试。

### 6.2 位姿漂移（训练毒药）

对遮挡校验后的 LAS 投影做逐帧偏移搜索（`experiments/diagnostics/pose_shift_search.py`）：

| 采集时间段 | 最优偏移中位数 |
|---|---|
| 0–10%（车棚角，即全部验证帧） | **4.8 px** |
| 10–60% | 4–5.7 px |
| 60–70% / 70–80% | 8.0 / 8.9 px |
| **80–90%** | **20.4 px（≈1°/在 6m 上 ~10cm）** |
| 90–100% | 4.0 px |

中后段恰是贴近房子 2–4m 的近距离绕行——**位姿误差在监督最密集处最大**。互相矛盾的
照片把 LiDAR 初始化的正确几何撕碎：H3 在自己**训练**视角上（6 个环绕方位，train split
103/226/314/362/224/61）agreement 仅 0.005–0.214、空洞 12.1%，26.7% 高斯不透明度
<0.005（濒死），死区空间上集中于房子中西部（`dead_gaussian_map.py` 的俯视图）。
车棚角位姿最好 → 只有那一侧"像训练过"。

### 6.3 波及范围

- H 阶梯、S/P/C/L 各系列的**同位姿相对比较仍然成立**，但只是"车棚角局部"的陈述；
  所有"全局质量/追平竞品"的解读作废。runs.csv 早已记录"agreement 奖励位姿一致性、
  跨流水线不可比"——同一机制反噬自身：我们对竞品的 agreement 优势一半是自家位姿
  自洽的假象。
- 竞品在同数据上做出了高质量全景 → 它的管线**解决了位姿问题**（训练中位姿优化或
  更好的相机-LiDAR 时间同步），这本身就是配方差距清单的一项，排在密度之后。

### 6.4 修复（q1_pose，已发车）

训练器本就有 `rig_pose_refinement`（每 rig 帧一个共享 SE3 修正、边界 0.25m/2°、
fail-closed 发布门）但从未启用。q1 = H3 配方 + 该项开启，单变量。判据顺序：
**六方位环绕 agreement/空洞**（故障在那里）→ 濒死率 → 车棚角能量（阶梯连续性）。
run_manifest 的修正分布应独立复现实测漂移形态；若修正≈0 则诊断错误。

### 6.5 【修正】主根因其实更简单也更严重：训练只用了 90 张验证图

用户追问"到底是不是在用所有相机看"之后复查训练器接线：**一旦配置
`face_cache_manifest`，训练监督完全来自 face cache**（`trainer.py` 1100 行，
`supervision: pinhole_faces`）。而 house0305 的 `face_manifest.json` 是
**`split: val`、只有 90 张图**——车棚角那 22 秒。h3 的 run_manifest 铁证：
`exposure_compensation.image_count = 90`。

即：**H1/H2/H3、S、P、C、L 所有 house0305 臂都只用 886 张里的 90 张训练，且
训练集=验证集（完全泄漏），"车棚角指标"是模型背自己的训练图**。另一侧不是被
坏位姿撕碎的——是**从未在训练中被渲染过**，加上 MCMC 噪声注入永不停（濒死高斯
随机游走成碎渣）。

事故机理：886 张的 face 产物早就全部在盘上（39.4GB，29238 个文件 = 886×33），
接入时某次用 `--split val` 重跑构建器，**幂等设计跳过产物但"每次重建并重签
manifest"**，把 manifest 覆盖成 val-only，796 张 train 产物成为孤儿。ukgs 的
cache 是 `split: train`（938 张，正确）——问题只在 house0305 接入。

层级修正：①主因=训练数据只有 10%（本节）；②次因=位姿漂移 8-20px（6.2 节，
测量独立成立，训练吃全量后必须处理，否则新加的 706 张会互相打架）；③度量盲区
=验证集塌缩（6.1 节）。q1（只修位姿、仍吃 val cache）作废终止；**q2 = 全量
train cache（796 张）+ 位姿精调**接替，训练前 fail-closed 校验 manifest 确为
train split。防复发：构建器应在 manifest 重签时若切分与现存产物覆盖范围显著
不符则给出显著警告（待做）。

### 6.6 事故附记（已修正定性）

发现时以为 GPU 上有"两份重复的 P1 训练互踩同一输出目录"，**该定性错误**：Windows
venv 的 `python.exe` 是 268KB 跳板，会以子进程拉起基础解释器（Python312），因此
每个 venv 进程都显示为 venv+系统 Python 的父子对——实际只有**一份** P1 训练链。
终止它依然正确（理由换成真的那个：它在用 90 张 val-only cache 训练，纯烧卡），
`p1_ppisp` 删除同理。教训：判"重复进程"必须先查父子链，venv 跳板会天然翻倍进程
数。P/S 系列在 q2 建立新基线后按需重跑。
