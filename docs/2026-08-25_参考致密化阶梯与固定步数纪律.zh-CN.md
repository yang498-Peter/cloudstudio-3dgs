# 2026-08-25 参考致密化阶梯：结论、两次误判，以及固定步数纪律

接《清晰度攻关与验收盲区》。本轮把自创的误差加权 MCMC 换成 gsplat 的原版
`DefaultStrategy` 并逐级加公开改进，同时补上了此前一直缺失的同步数基线。

**先说结论**：致密化在同步数下**仍然是净负**（0.326 → 0.304），但代价比 7000 步时
减半，且减半是 AbsGS 带来的。画质判据上最好的依然是不做致密化的配置。

## 一、最终格局（全部 16000 步，全部读 `latest.pt`）

| 配置 | 一致性 | 能量 | 空洞率 | 高斯数 |
|---|---|---|---|---|
| **R0 不致密化** | **0.326** | 0.194 | 7.1% | 390k |
| R2 AbsGS | 0.304 | 0.203 | 6.5% | 1.80M |
| R1 原版判据 | 0.282 | 0.195 | 8.1% | 1.08M |
| R4 AbsGS + 两个 2d 通道 | 4600 步增长失控中止 | | | 3.07M |

7000 步的历史参考：S0 不致密化 0.339，D1 自创采样 0.291。

三个可行动的读数：

1. **致密化仍净负，但差距从 0.048 缩到 0.022**，缩小的那一半来自 AbsGS。
2. **R0 用 39 万高斯打赢 R2 的 180 万。** 这是 WP-6 固定容量结论在清晰度判据上的
   复现——此前只在五表平均值上看到过。
3. AbsGS 是唯一超过 D1 的致密化配置，方向有效。

## 二、误判一：`best_golden` 冻结，把排名整个倒过来

`golden_evaluation.max_floater_count`（2600）拒绝任何漂浮物超标的检查点，
`best_golden.pt` 因此停在最后一个合格步——而验收管线和 `sharpness_metrics`
默认读的就是它。

```
R1  交付 step 7000 / 训练 16000    漂浮物到 16000 步涨到 4,680
R2  交付 step 1000 / 训练 16000    漂浮物到 16000 步涨到 10,131
```

| | best_golden 读数 | latest.pt @16k |
|---|---|---|
| R1 | 0.289（7000 步模型） | 0.282 |
| R2 | **0.185（1000 步模型）** | **0.304** |

R2 的误差 0.119，方向相反。按错误读数我曾判定"AbsGS 严重有害"，实际它是全场最佳
致密化臂。**整个 phase-14 的自动判词因此作废。**

日志全程没有任何警告：`golden_history.json` 照常记录逐步上升的 PSNR，12000 步的
16.292 是 R1 全程最佳外观，从未被测量过。

**已定为纪律：A/B 对比一律用 `latest.pt` 固定步数。**`best_golden` 回答的是
"在漂浮物预算下该发布哪个模型"——产品决策，不是方法排名。

已落地的防线：`run_manifest` 记录 `delivered_step_fraction` 与门槛拒绝次数；
`sharpness_metrics` 打印"这个检查点是第 N 步 / 请求 M 步"并在有差距时明说。
选择逻辑没有放宽——漂浮物确实是画质缺陷，该修的是它上游。

## 三、误判二：打开"剪枝"同时打开了一个不看梯度的增长通道

R4 想用上游的屏幕空间剪枝压住漂浮物，4600 步长到 306 万中止。原因在上游源码：

```python
is_split |= state["radii"] > self.grow_scale2d     # 无条件 OR
```

这一句**完全不看梯度**：任何投影超过图像 5% 的高斯仅凭尺寸就分裂。而
`refine_scale2d_stop_iter` 同时门控增长和剪枝两条通道——打开"剪枝"就等于打开了
一个纯尺寸驱动的增长源，在近距离鱼眼场景里立即复利。

上游注释还写明：原版 3DGS 的屏幕空间剪枝**因为一个 bug 从未真正运行**
（graphdeco-inria/gaussian-splatting#123），gsplat "为完整性实现但默认设 0 禁用"。
**所以两条通道都不属于原版 3DGS 的实际行为**，只开剪枝那一半是明确的选择而非复现。

R5 保留 `prune_scale2d=0.15`，用 `grow_scale2d=10.0` 让增长子句永不触发
（radii 按图像尺寸归一化，10 个图像宽度不可能跨过）。

**当天新加的容量止损把这次失控变成了一句可归因的诊断**，而不是几小时后一个
无法解释的 CUDA OOM。

## 四、本轮修好的接线（都会静默失效）

| 问题 | 后果 | 修法 |
|---|---|---|
| `scene_scale` 传成高斯尺度中位数 | split 阈值变 0.58mm，全部劈碎 | 配置改显式米制，`state_dict` 记录解析后米数 |
| 致密化判据微分总损失 | LiDAR 项污染出生判据 | `densification_gradient_source="rgb_only"` 两段 backward |
| 法线锚点在致密化后失效 | 新分裂高斯恰好无约束 | 事件驱动刷新 + `normal_loss_active_ratio` 证据（实测 100%） |
| 阈值驱动增长无上限 | 数小时后 OOM | 容量止损，超限即中止并报出步数与数量 |

## 五、附带处理

磁盘曾满（C 盘剩 4GB）导致 R3 崩溃，`WinError 32` 是写 checkpoint 的次生现象而非
文件锁冲突。删除 40 个已判决探针的 `best_golden.pt` 回收 47.6GB，**保留每个 run 的
`latest.pt`**——今天的教训正是 latest 才是可重测的那一个。

新增实时仪表盘（`scratchpad/dashboard.py`，端口 8791），读训练已经写出的产物，
判决表按固定步数取数并标出交付步数缺口。它上线第一分钟就抓到自己在显示一份上一轮
已撤回运行的陈旧结果。
