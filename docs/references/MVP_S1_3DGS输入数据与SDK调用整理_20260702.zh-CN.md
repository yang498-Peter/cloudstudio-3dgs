# MVP S1 3DGS 输入数据与 SDK 调用整理

整理时间：2026-07-02

参考软件：`G:\S1\3DGS\Tersus-GNSS-MVP-S1-3DGS-Processor-V1.0.0-alpha2-20260608B`

参考样例：

- Raw scan：`G:\S1\2026-06-21_13-29-13house2`
- Solved/process：`G:\S1\2026-06-21_13-29-13house2\process\2026-06-21_13-29-13house2`
- 之前成功 3DGS 输出：`G:\Tersus3DGSResults\20260609-234131-s1-3dgs`

## 1. 总体结论

这个成品软件并不是把 MVP S1 原始 `data_raw.mcap` 直接喂给 3DGS SDK。它的实际流程是：

1. 读取 MVP S1 raw scan folder，拿到双目相机图片、设备信息、相机标定、实时点云。
2. 读取已经求解过的 `process/<project>/` 目录，拿到 `ImgPose.txt`、`transforms.json`、`odom.csv`、彩色 LAS。
3. 软件把这些内容转换成 SDK 需要的 `task.json`。
4. 调用第三方 SDK：

```text
reconstruct_full_engine.exe --reconstruct_type 1 --task_json <task.json>
reconstruct_full_engine.exe --reconstruct_type 2 --task_json <task.json>
```

默认两阶段运行。软件日志里把第一阶段称为 initial alignment，第二阶段称为 model generation。

对自研算法来说，最重要的数据契约不是这个 SDK 的完整 `task.json`，而是下面这些基础输入：

- 双目图片：`camera/left/*.jpg`、`camera/right/*.jpg`
- 相机内参和畸变：`info/calibration.json` 或 `transforms.json`
- 每张图片外参：`ImgPose.txt` 或 `transforms.json`
- 彩色点云：`colorized.las` / `<project>_colorized.las` / `colorized-realtime.las`
- 可选轨迹：`odom.csv` / `odom-realtime.csv`
- 项目和设备元数据：`metadata.yaml`、`info/device_info.json`

## 4. 相机标定格式

`info/calibration.json` 是双目 fisheye 标定。核心字段：

```json
{
  "version": "v2",
  "cameras": [
    {
      "name": "left",
      "type": "fisheye",
      "width": 2912,
      "height": 2912,
      "intrinsic": {
        "fl_x": 777.4788779034258,
        "fl_y": 777.7524641168766,
        "cx": 1453.9369883854906,
        "cy": 1450.786805386424
      },
      "distortion": {
        "camera_model": "OPENCV_FISHEYE",
        "params": {
          "k1": 0.08179302700881765,
          "k2": -0.011926722405662877,
          "k3": -0.002896186185757192,
          "k4": -0.00012363296834601707
        }
      },
      "transform_from_lidar": {
        "rotation": [[...], [...], [...]],
        "position": [0.02134455437285915, -0.07270766306350844, -0.03258741738574701]
      }
    }
  ]
}
```

软件转给 SDK 的相机模型字段：

```json
{
  "id": 1,
  "meta_data": {
    "camera_name": "left",
    "projection_model": 1,
    "width": 2912,
    "height": 2912,
    "parameters": [
      "fl_x", "fl_y", "cx", "cy", "k1", "k2", "k3", "k4", 0, 0
    ],
    "constant_parameters": []
  }
}
```

注意点：

- SDK 里 `projection_model: 1` 应该代表 fisheye/特定相机模型，但需要 SDK 文档确认。
- 软件把 `k1..k4` 直接传入，不做去畸变后再训练。
- `transform_from_lidar` 对 3DGS task 不是直接传给 SDK 的核心字段；SDK task 主要用图片 pose 和 LAS。

## 5. Pose 文件：ImgPose.txt

`ImgPose.txt` 是软件默认优先使用的图片外参来源。

文件头：

```text
index x y z roll pitch yaw qx qy qz qw timestamp
```

样例行：

```text
left/1782045009842132736.jpg 0.544695308947756 -0.321467840830897 0.655661050097033 -88.068561241428 1.171345409049 118.260687976142 -0.362929753724143 -0.592818458359028 0.620692189632820 0.362752636130150 1782045009.842132806778
```

软件解析规则：

- 第 1 列必须指向 `left/...` 或 `right/...`。
- 第 2-4 列是相机位置 `x y z`。
- 第 8-11 列是四元数 `qx qy qz qw`。
- 第 12 列是 timestamp。
- `roll/pitch/yaw` 被读取但没有用于生成 SDK task。
- 四元数会检查 norm，必要时归一化。
- 缺 pose 的图像默认会被排除，而不是直接失败。

软件内部对 `ImgPose.txt` 的 pose 做了一个相机轴约定转换：

```text
orientationConvention: imgpose_world_to_camera
orientationMode: transpose
```

生成 SDK task 时，单张图片会变成：

```json
{
  "id": 1,
  "path": "G:\\S1\\...\\camera\\left\\1782045009842132736.jpg",
  "meta_data": {
    "width": 2912,
    "height": 2912,
    "camera_id": 1,
    "pos": [0.544695308947756, -0.321467840830897, 0.655661050097033],
    "pos_sigma": [0.03, 0.03, 0.06],
    "orientation": [
      -0.4733850376847195,
      -0.02001254183866452,
      -0.8806282440765754,
      0.8806183702201378,
      -0.033953600818904084,
      -0.472608124160238,
      -0.020442410011178913,
      -0.9992230237342343,
      0.033696538581115876
    ],
    "pre_calib_param": ["fl_x", "fl_y", "cx", "cy", "k1", "k2", "k3", "k4", 0],
    "timestamp": 1782045009.8421328
  }
}
```

## 6. transforms.json

`transforms.json` 是备用 pose 和标定来源，格式接近 NeRF/3DGS 常见格式。

样例 frame：

```json
{
  "cx": 1457.1928405553294,
  "cy": 1456.3678316148116,
  "file_path": "left\\1782045009842132736.jpg",
  "fl_x": 790.4331310764682,
  "fl_y": 790.5911457239083,
  "h": 2912,
  "k1": 0.07978275515522047,
  "k2": -0.003644391555582949,
  "k3": -0.009725430508335905,
  "k4": 0.001475794307886328,
  "timestamp": 1782045009842132736,
  "transform_matrix": [
    [-0.47338432554034965, 0.02001995586209227, 0.8806284583750338, 0.5447506382485039],
    [0.8806185257957589, 0.033968653796881854, 0.4726067525803381, -0.32146824491480086],
    [-0.020452196899438512, 0.999222363604072, -0.03371017228492187, 0.655803200838421],
    [0, 0, 0, 1]
  ],
  "w": 2912
}
```

软件逻辑：

- 默认优先 `ImgPose.txt`。
- 如果没有 `calibration.json`，可以从 `transforms.json` 第一帧 left/right 中提取相机内参。
- 如果没有 `ImgPose.txt`，可以用 `transforms.json` 的 frame pose。

自研算法建议直接支持 `transforms.json`，因为它更接近训练框架常用输入。

## 7. 点云输入：LAS

软件识别 LiDAR 的优先级：

1. 显式选择的 `lidarPath`。
2. solved/process 目录中的 `colorized.las`。
3. raw 目录中的 `colorized.las`。
4. solved/process 目录中的 `colorized-realtime.las`。
5. raw 目录中的 `colorized-realtime.las`。
6. raw 目录 `data/colorized.las`。

实际样例 process 目录里是：

```text
2026-06-21_13-29-13house2_colorized.las
2026-06-21_13-29-13house2_uncolorized.las
```

这种带项目前缀的 LAS 需要 UI 显式选择，否则自动规则不一定能命中。

样例 LAS header：

```json
{
  "signature": "LASF",
  "version": "1.4",
  "headerSize": 375,
  "pointOffset": 667,
  "pointFormat": 7,
  "recordLength": 36,
  "scale": [0.0001, 0.0001, 0.0001],
  "offset": [0, 0, 0]
}
```

软件要求：

- LAS 必须可读。
- 必须有 RGB color fields。
- 如果运行时是 `sdks/bin` 这种完整 SDK 结构，软件会把 LAS 1.4 / point format 7 自动转换为 LAS 1.2 / point format 3，输出到：

```text
<runDir>\prepared-input\colorized.las
```

这个兼容转换对第三方 SDK 很关键。自研算法如果直接读 LAS 1.4 PF7，可以跳过转换；如果依赖旧 LAS reader，则需要类似兼容层。

## 8. 轨迹输入：odom.csv

`odom.csv` 样例头：

```text
#timestamp, x, y, z, q_x, q_y, q_z, q_w
```

样例行：

```text
1782045009547616160,0.560102950396501,-0.316641760336224,0.685263110676586,-0.152329097013098,0.071579863671819,0.936191945017422,0.308572214245537
```

成品软件默认：

```text
includeLidarTrajectory: false
```

也就是说当前 3DGS SDK task 默认不把 LiDAR trajectory 传入。代码里保留了读取 `odom.csv` 的能力，但 desktop 模式强制关闭 trajectory。

自研算法建议：

- 第一版可以不依赖 odom，只用图像 pose + 彩色点云。
- 后续可以用 odom 做时间同步检查、轨迹平滑、pose prior 或局部尺度约束。

## 9. 图像配对与采样策略

软件不是直接使用全部图片，而是：

1. 读取 left/right 图片。
2. 根据 timestamp 匹配最近的左右图。
3. timestamp 很大时，左右匹配容差是 `50_000_000`；普通秒级 timestamp 容差是 `0.05`。
4. 默认均匀采样 `935` 对。
5. 每对输出 left/right 两张图，因此默认 task 约 `1870` 张图。

样例 `house2` 的 build summary：

```json
{
  "requestedPairs": 935,
  "pairedCount": 935,
  "matchedPairCount": 974,
  "imageCount": 1870,
  "excludedImageCount": 6,
  "availableCameraImageCount": 1954,
  "availableLeftImages": 974,
  "availableRightImages": 974
}
```

自研算法建议：

- 数据导入层保留全量 pairs。
- 训练层提供采样策略：全量、均匀采样、按运动距离采样、按视角变化采样。
- 缺 pose 的图片默认剔除，并记录清单。

## 10. SDK task.json 核心结构

软件生成的 SDK task 顶层字段：

```json
{
  "working_dir": "...",
  "gdal_folder": "...",
  "pipeline_mode": 1,
  "input_image_type": 1,
  "resolution_level": 1,
  "coordinate_system": {
    "type": 1,
    "type_name": "LOCAL",
    "label": "本地坐标系",
    "origin_point": null
  },
  "camera_meta_data": [],
  "image_meta_data": [],
  "lidar_data": {},
  "generate_osgb": true,
  "generate_las": true,
  "generate_pc_pnts": true,
  "generate_gs_ply": true,
  "generate_gs_splat_sog_tiles": true,
  "remove_moving_object": true,
  "resumable_reconstruction": true
}
```

关键字段解释：

- `camera_meta_data`：left/right 相机内参、畸变、图像尺寸。
- `image_meta_data`：每张图的路径、相机 id、pose、timestamp、pre-calib 参数。
- `lidar_data.laser_meta_data`：彩色 LAS 路径。
- `coordinate_system`：本地坐标系，不是地理坐标系。
- `pos_sigma`：默认 `[0.03, 0.03, 0.06]`，可理解为位置先验不确定度。
- `orientation`：3x3 rotation flatten 后的 9 个数。
- `pre_calib_param`：`[fl_x, fl_y, cx, cy, k1, k2, k3, k4, 0]`。

## 11. SDK 调用与运行前检查

软件启动 SDK 前做：

1. 输入检查：相机目录、标定、pose、LAS、SDK DLL 是否存在。
2. 硬件检查：

```text
hardware_check.exe
```

3. 授权检查：

```text
license_engine.exe --bind <licenseKey>
license_engine.exe --enum <license.json>
```

4. 生成 `task.json` 和 `task.summary.json`。
5. 调用：

```text
reconstruct_full_engine.exe --reconstruct_type 1 --task_json <task.json>
reconstruct_full_engine.exe --reconstruct_type 2 --task_json <task.json>
```

默认 `reconstructTypes` 是 `[1, 2]`。可以通过配置或环境变量覆盖。

## 14. 后续研发重点

自研算法最需要先解决这些问题：

1. Pose convention 固化：明确 `ImgPose.txt` 四元数是 world-to-camera 还是 camera-to-world，以及当前软件的轴转换矩阵。
2. Fisheye 支持：选择直接 fisheye projection 训练，还是先 undistort 成 pinhole。
3. LAS 初始化策略：彩色 LiDAR 可用于初始化 Gaussian 点、尺度范围、裁剪边界、颜色先验。
4. 双目利用方式：可以只把 left/right 当独立多视角，也可以显式利用 stereo pair 约束深度。
5. 采样策略：默认 935 对是 SDK/性能折中，不一定是算法最佳。
6. 大模型输出格式：`gs_full.ply` 很大，必须从一开始设计压缩、tile、LOD 或流式加载。
7. 质量诊断：必须检查 sky-only、缺 pose、LAS 无 RGB、坐标尺度异常、timestamp 对不齐。

## 15. 已确认的软件适配细节

- 默认 `samplePairs: 935`。
- 默认 `imagePoseSource: "imgpose"`。
- 默认 `sampleStrategy: "even"`。
- 默认 `taskInputMode: "desktop"`。
- 默认 `includeLidarTrajectory: false`。
- 默认 `includeImagePose: true`。
- 默认 `excludeImagesWithoutPose: true`。
- 默认 `orientationMode: "transpose"`。
- 默认 `resolutionLevel: 1`。
- 默认 `posSigma: [0.03, 0.03, 0.06]`。
- 默认输出包含 `generate_gs_ply: true` 和 `generate_gs_splat_sog_tiles: true`。
- SDK 路径依赖 `sdks/bin/reconstruct_full_engine.exe`、`hardware_check.exe`、`license_engine.exe`、`gdal_data`。
- SDK 对路径编码敏感，之前中文路径下 `gdal_folder` 触发过失败；研发和交付应优先使用 ASCII 安装路径。
