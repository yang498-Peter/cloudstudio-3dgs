### 2.1 两条路线（2026-10-06 核实）

门禁链与位姿是绑定的，所以"新数据"实际有两条路：

| | 生产路线（house0305 SOP） | 快速路线（原始位姿） |
| --- | --- | --- |
| 位姿 | 独立 AT（hloc → 三角化 → independent AT / rig BA → BA 训练清单） | S1Mapper `ImgPose.txt` 原样 |
| 门禁 | 必须：`build_mipmap_frontend_gate.py` 要求完整三角化、AT 收敛、训练清单由 AT 发布（:196-225）；训练器对 AT 血统数据强制要门禁（`trainer.py`:1953-1964） | 不需要：训练器只对 AT 血统数据要求门禁 |
| 切块 | 自适应 kd 规划器，必须吃天空门禁或 LiDAR 深度门禁（`build_lidar_face4_adaptive_tile_plan.py`:98-108） | SDK 条带切块 + 用 `lidar_face4_observations` 投影绑定每切块视角（不依赖门禁） |
| 画质 | 交付级 | 受位姿误差限制（0614 边缘对齐中位 25 px），只用于验证工具链 |
| 新增工作 | W10 从"远期"变为必需：AT 链编排进 SDK | W2 改为"条带切块 + 视角绑定"，约 1 天 |

建议顺序：先做快速路线，让 0614 子集端到端跑通，验证缓存、配方、训练、交付整条链的通用性；再补 AT 编排走生产路线。

### 2.2 在 house0614 上预检暴露的三个通用性缺陷（2026-10-07，已修）

1. **拆分采集无法估算**：dry-run / preflight 的估算路径丢了 `--run-dir` 与 `--adapter`，0614 这种图像与位姿/点云分两个目录的采集根本算不出计划。现在 `load_capture`、`estimate_dataset_summary`、`Project.dataset_estimate` 与 `preflight` 命令都带上它们。
2. **切块数写死为参考值 4**：1 亿点切 4 块，每块初始化约 2570 万点，超过 15M 上限，训练器会在启动时拒绝，而这要等约 40 小时的 prepare 跑完才暴露。现在切块数按 cap 规则自动定（`tile_count_for`：点数×1.05 晕圈×1.756×1.5 ÷ 上限，不少于参考值；house0305 在所有 profile 下仍为 4，0614 为 19）；预检新增 `tile_capacity`（初始化 ≥ cap 时 FAIL 并给出所需切块数，cap 低于比例时 WARN）。
3. **单轴条带切不出多块**：19 条带在最密处只有 0.89 m 宽，触发最小宽度拒绝；即便合法也是 5–7 m 宽、整场长的细条，不利训练。新增 `grid` 布局：沿长轴按"每条带要切的格数"加权等点数切条带，条带内再沿短轴按该条带自身点分布等点数切格（2D 占用直方图，512×512）；格子近方、点数近等，通过训练器的切块计划校验与归属分区校验。只在切块数超过参考值时使用，条带计划的 `to_dict` 不记录 layout，所有已有计划摘要不变。

**仍开着的问题（不自动处理）**：0614 每块 4.6k–7.2k 训练视角，而配方的 30k 停点是在每块 1.7k–2.3k 视角上调的（每视角约 13–18 次访问 vs 0614 约 4 次）。计划会给出警告（profile 开放问题 `views-per-tile`）；加块还是延长停点没有测量依据。

### 2.4 AT 位姿链的已知边界（2026-10-08）

- **UK 采集首次从原始 S1 位姿跑通（2026-10-08，经 SDK 自己的接入图）。** house0305 的 AT 起点是手工套用 rig BA 后的位姿；UK 直接从 S1Mapper 原始 POS 起步：原始层 → 6962 对 → 两遍特征（13.2 / 11.8 min）→ 三角化（1044 张全部注册，48.8 万点，5.4 min）→ 独立 AT 在第 92 次外层迭代收敛（158.5 min），重投影 p50 1.40 → **0.874 px**、p95 3.31 → 2.46 px（house0305 被接受的 AT：1.36 → 1.01 px），位置修正 p50/p95/最大 8.5/18.7/28.7 mm，旋转修正 p50 0.18°；时间同步模型 12.4 min、审计 7.1 min，最优偏移 0 ms（−10/−5 ms 显著变差，+5…+20 ms 不显著，82 帧）；训练清单（938/106）、训练层遮罩、人物遮罩重绑定、划分全部通过。过程中修了三处：KB4 判定（见下条）、80 次外层迭代不够（第 80 次步长 1.85e-6 对 1e-6，改为上限 200、容差不变）、未收敛的已签名报告被当成已完成（新增 `requires` 内容要求）；另有两处接线错误：审计加载器的颜色模型默认值（`sh`）与训练器（`rgb_sigmoid`）不一致、`build_ba_training_manifest.py` 的 `--output` 是目录。face 缓存、深度、门禁链与烟测需约 130 GB，本机磁盘不够，仍未在真数据上跑。
- **AT 工具的内参判定缺陷（已修，1a3c90e）**：KB4 内参求解最小化的是 Huber 代价，工具却要求普通 RMSE 上升不超过 1e-9 px；接近收敛时 Huber 代价下降而 RMSE 只有浮点抖动，UK 采集的独立 AT 因此在第 112 分钟被判失败（"Both ftol and xtol termination conditions are satisfied; RMSE 0.913865 -> 0.913865 px"）。现改为 Huber 代价不得上升、RMSE 上升不超过 1e-5 px，真正变差的求解照样拒绝。
- **时间同步审计的模型是短训练**（手册 A1 的替代方案，未验证统计功效）；house0305 用的是 3 万步交付模型。审计只在显著时才选非 0 偏移，弱模型更可能保持 0。
- **门禁的 `authorized_scope.capacity_cap` 训练器不执行**；SDK 用 Tile_0 按 profile 规则算出的 cap 跑烟测，记录的是实际测得的全分辨率峰值显存。
- **重新切块必须从 gate_12 之后重建**（切块门禁、归属、烟测、晋升、绑定 DA2）；门禁链记录全部输入指纹，任何输入变化都从 gate_10 重建。

### 2.5 无人值守长跑的流程加固（2026-10-09，未跑真实数据）

一次交付约 40 小时无人值守，这一轮只改流程和 SDK，不改配方，没有跑任何真实训练。

1. **训练步的完成判定（缺陷修复）**：训练器每 `checkpoint_every`（5000）步覆写一次 `latest.pt`，SDK 却以"产物存在"判定训练步完成。中途崩溃（本机 2026-09-25 出现过 0x116 蓝屏）后重跑，会把第 15000 步的半截检查点当成训练完成，直接送去背景渲染与合并。现在训练步（`PlannedStep.pipeline_arm`）只认 `tools/pipeline.py` 已验证的 `TRAINING_COMPLETE`，验证依据是检查点、退出原因、mtime 与步数四类证据。
2. **原地续训**：同一冻结配置的上一次尝试已不在运行、留下可加载且未到目标步数的检查点、失败原因不是 OOM 时，流水线用 `train_gsplat.py --resume-checkpoint` 从该臂自己的检查点继续。恢复的是训练器自带的 `resume_checkpoint`：优化器、采样器、策略与遥测状态一起恢复，检查点身份按配置核对。冻结配置一个字节都不改；续训记录在作业状态（`resumed_from`）和台账里，上一次的日志改名保留。OOM 不续训，因为同样的种群会再撞同一面墙；配置不同、检查点损坏或到达目标步数时也不续训。续训与不中断的运行并非逐位一致（重跑噪声本来就有 ±3%），这一点由记录保证可追溯。另一种中断是流水线进程先死、训练器自己跑完：此时作业停在 RUNNING，过去重跑会全新启动并撞上非空输出目录。现在先按四类证据验收它留下的检查点，通过就记为完成，不再重训。读检查点之前先扫描存活的训练进程：孤儿训练器可能还在写同一个文件，读者占着句柄会让它的 os.replace 失败并把它杀掉。
3. **`run --work W` 原样续跑**：`run` 把启动参数（数据集、profile、位姿路线、资产、环境脚本等）写进 `<work>/sdk_state/invocation.json`。之后 `run` 或 `status` 没给的参数从这里补，显式参数优先，并打印补了哪几项。重启后只需 `python -m cloudstudio3dgs_sdk run --work W`。
4. **`status` 命令**：`python -m cloudstudio3dgs_sdk status --work W [--json]` 只读，不启动任何东西。它按与执行器相同的判定列出各阶段的完成/总步数、下一步和剩余时间；从训练器的 `monitor/progress.jsonl` 读出正在训练的臂的步数、速率、ETA 和高斯数；未在运行的臂会说明下次运行是续训还是从头训练；另外列出 GPU 租约持有者、最新日志的最后一行，以及剩余所需磁盘与可用空间。
5. **阈值对照只计数**：交付的阈值对照过去在 0/0.01/0.05 三个阈值各导出一份完整 PLY，只为读顶点数。现在导出工具新增 `--count-thresholds`，与导出共用同一套行选择（`_keep_mask`，测试逐阈值、逐分层核对二者计数相等），一次加载、不写 PLY。UK 估算：交付阶段磁盘 27.4 → 15.8 GB，总峰值 133.7 → 122.1 GB（含 ×1.25 余量为 167 → 153 GB）。
